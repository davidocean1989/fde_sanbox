# 结构化输出解析管道 · 实验总结

| 项 | 值 |
|---|---|
| 项目 | `fde_sanbox/w2` |
| 日期 | 2026-11-19 |
| 环境 | Python 3.12.14 / pytest 9.2.0 / pydantic 2.14.0 |
| 数据 | `probes.json` 20 条探针；`probes.jsonl` 40 行（本轮弱 prompt 两组） |
| 测试 | 4 个用例，全部通过（0.31s） |

---

## 0. 一句话结论

回喂机制首次在真实 API 链路上被触发并验证：弱 prompt 下结构通过率 **0/20 → 20/20**，净效果 +20 条。但同一批数据证明：**`final_ok` 只衡量结构合法性，不衡量分类正确性**——与强 prompt 词表版相比，主题判定仅 **8/20 一致**。`parse()` 对语义一无所知。

---

## 1. 实验目标

本轮要回答三个问题：

1. 回喂（把坏输出原文 + 校验错误追加进 messages 再问一次）到底能不能把非法输出救回来？
2. 救回来的代价是什么（调用次数、延迟、质量）？
3. `final_ok = true` 能不能当作"这条分类正确"？

## 2. 被测系统

### 2.1 四段职责划分

| 模块 | 职责 | 明确不做 |
|---|---|---|
| `schema.py` | 定义 `TopicResult`（topic / confidence / reason） | 不解析、不校验业务语义 |
| `parse.py` | 不可信字符串 → 可信对象，**全项目唯一信任转换入口** | 不碰网络、不碰 message、不写文件 |
| `pipeline.py` | 组装 messages、重试编排、写入 jsonl | 不判断分类对错 |
| `client.py` | 真实 API 调用与网络层重试 | 不关心结构校验 |

### 2.2 `extract_one` 的三条出口

```
message = [system(BARE/SYSTEM), user(probe)]      ← 唯一可变状态，循环外只建一次
for attempt in range(max_repair + 1):
    res = llm_complete(message, temperature=0)           ← LLMResult（具名对象）
    usage_log.append(res.usage)                          ← 每轮都记，成功失败都算钱
    raw = res.content
    try:
        obj = parse(raw)
    except ParseError as e:
        last_kind, last_error = e.kind, e.message
        message += [ assistant(raw), user(RETRY_HINT + e.message) ]   ← 回喂
        continue
    return Result(final_ok=True, repair_count=attempt)                ← 出口 1 / 2
raise RepaireExhausted(Result(final_ok=False, ...))                  ← 出口 3
```

| 出口 | 触发条件 | 返回形态 |
|---|---|---|
| 出口 1 | 第一次 `parse` 成功 | `Result(final_ok=True, repair_count=0)` |
| 出口 2 | 第 N 次（N≥1）成功 | `Result(final_ok=True, repair_count=N)` |
| 出口 3 | 所有轮次全失败，循环自然结束 | `raise RepaireExhausted`，异常携带完整 `Result` |

关键设计：`raise` 写在 `for` 外面、没有 `if` 判断——因为任意一轮成功就已经 `return` 了，能走到那一行必然是全部失败。位置本身就是条件。

### 2.3 接缝设计

```python
LlmFn = Callable[[list[dict], float], LLMResult]   # 2 进 1 出：messages + temperature → 具名结果对象
```

返回契约定义在零依赖的 `contracts.py`（不绑在 `client.py` 上，避免测试导入契约时连带触发 `OpenAI()` 初始化）：

| 对象 | 字段 | 口径 |
|---|---|---|
| `Usage` | `prompt_tokens / completion_tokens / total_tokens: int \| None`、`raw: dict \| None` | `None` = 拿不到，**不是 0**；`raw` 留 provider 原始 usage 供跨厂商归一 |
| `LLMResult` | `content: str`、`usage`、`latency_ms`、`model`、`finish_reason` | `LlmFn` 唯一返回类型；空回复兜底 `""` 而非 `None` |
| `sum_usage()` | `list[Usage] → (聚合 Usage, 缺失次数)` | 总体 token = **Σ 每轮**；回喂时 `prompt_tokens` 逐轮增长也必须算进去 |

`fake_llm(script, usage_script=None)` 返回 `(_fn, calls)`，导演 / 演员 / 场记三分：

| 角色 | 对象 | 说明 |
|---|---|---|
| 台词本 | `script` | 第 N 次被调用时该说什么，播种时固定 |
| 演员 | `_fn` | 每被调一次，念一行台词、记一笔场记 |
| 场记本 | `calls` | `list[list[dict]]`，外层=调用次数，中层=那次的 messages 快照 |
| 导演 | `pipeline` 的 `for` 循环 | 喊"上台"、决定要不要喊第二次 |

三个必须记住的点：

- **`append` 一次只加 1 个元素**。`calls.append([dict(m) for m in messages])` 是把整份快照当一个元素塞进去 → 三层结构；写成 `extend` 就摊平成两层，`len(calls)` 立刻失真。
- **`min(len(calls)-1, len(script)-1)` 是按调用序号取，不是取最后一项**。剧本用完才钳住索引，所以"一直坏"这种状态只需写一行剧本。

- **`usage_script` 按轮次给 token 剧本**：默认每轮 `10/5/15`，所以 act2 断言 `total_tokens == 30` 直接验出「累加而非最后一轮覆盖」；传 `None` 那一轮只计 `usage_missing`，不虚增成本。

### 2.4 错误分类表（`parse.py` 的 `_KIND`）

| pydantic 错误码 | kind | 含义 |
|---|---|---|
| `json_invalid` | `syntax` | 围栏 / 单引号 / 尾逗号 / 解释文字 |
| `literal_error` | `enum` | 自造主题名 |
| `missing` | `missing` | 字段缺失或字段名不对 |
| `string_too_short` | `empty` | reason 空壳 |
| `less_than_equal` / `greater_than_equal` | `range` | confidence 越界 |

## 3. 实验设计：3×2 矩阵

| | `max_repair=0`（关回喂） | `max_repair=1`（开回喂） |
|---|---|---|
| 强 prompt · 无词表 | 20/20 · repair 全 0 · unknown **10** | 20/20 · repair 全 0 · unknown **10** |
| 强 prompt · 词表版 | 20/20 · repair 全 0 · unknown **1** | 20/20 · repair 全 0 · unknown **2** |
| 弱 prompt · BARE | **0/20** · missing 20 · output 全 null | **20/20** · repair 全 1 · unknown **8** |

- 控制项：同一批 20 条探针、`temperature=0`、同一 provider / 模型。
- 自变量：prompt 强度（强词表版 / 弱 BARE）、是否允许重试回喂。
- 因变量：`final_ok`、`repair_count`、`error_kind`、`topic`、`latency_ms`。
- 三版 prompt 体量：词表版 1845 字符 / 经典强版 868 字符 / BARE 64 字符（约 29 倍差）。

| `output` | 全 `None` | 全有值 |

### 4.2 第一次输出（baseline）的三种坏法

20 条全部是**合法 JSON**（`input_type=dict` 20/20），`_strip_fence` 与 `json.loads` 一层都没拦到，挂在 pydantic 字段校验：

| 坏法 | 条数 | 说明 |
|---|---|---|
| 给了 `possible_themes` 候选数组 | 10 | 模型"拿不准就多给几个" |
| 字段名写成 `theme` 而非 `topic` | 6 | 弱 prompt 没规定字段名 |
| 外面套一层 `analysis` | 4 | 自作主张加结构 |

### 4.3 主题判定与强 prompt 词表版的一致性

一致 **8/20（40%）**：probe `0,1,2,3,6,8,15,19`。

## 5. 结论

**结论 1｜回喂在真实链路上有效，且效果显著。**
弱 prompt 下结构通过率 `0/20 → 20/20`，20 条全部恰好重试 1 次成功（`repair_count` 全 1）。出口 2 此前只在假模型（act2）里跑过，这是第一次被真实 API 走到。

**结论 2｜`final_ok` 只证明结构合法，不证明分类正确。**
40 行数据里 20 行 `final_ok=true`，但与强 prompt 词表版相比只有 8/20 一致。两个维度必须分开记账：

| 维度 | 守卫者 | 本轮数值 |
|---|---|---|
| 结构合法性 | `parse()` → pydantic | 20/20 |
| 分类正确性 | 无人守 | 8/20（且只是"与参照版一致"，不是准确率） |

**结论 3｜真实模型的坏输出是 `missing`，不是 `syntax`。**
假模型剧本里写的是单引号、尾逗号、代码围栏，全是 `syntax`；真实模型在弱 prompt 下**不犯语法错**，它犯的是"没遵守输出契约"——字段名错、多包一层、给候选数组。20/20 全部落在 `missing` 分支，这是 `_KIND` 表里此前从未被真链路覆盖的一支。

**结论 4｜回喂修的是格式契约，修不回被删掉的语义知识。**
`RETRY_HINT` 明确列出 `topic / confidence / reason` 三个字段名与 7 个合法主题，加上 `e.message` 点名 `topic Field required`，所以第二次能改对字段。但它不提供主题定义——BARE_PROMPT 只给了 `fde/hulu/rag`，`zfc/wechat/live/public` 模型根本不知道存在，只能推去 `unknown`（8 条里 6 条是这个原因）。

**结论 5｜主题定义缺失时，模型会编造缩写含义。**
FDE 被解释成「前端开发工程」「渐进式知识管理」「故障检测与排除」；备孕检查判 `fde`，理由是「家庭健康管理」。这些 reason 表面自洽，实则全是幻觉，且 pydantic 一个字段都拦不住。

**结论 6｜prompt 完善度决定回喂是否需要。**
强词表版两组 `repair_count` 全 0——格式已经稳定，回喂是纯冗余（但成本也是 0，因为不触发就不调第二次）。弱 prompt 才让回喂的价值显形。**回喂是兜底，不是能力来源。**

**结论 7｜`temperature=0` 不等于完全确定。**
强词表版两组逐条比对：topic 19/20 一致，probe 16 在 `rag 0.7` 与 `unknown 0.0` 之间翻转；另有 6 条 reason 措辞不同。分类结论较稳，措辞会漂——不要拿 reason 文本做精确断言。

**结论 8｜`reason` 的「必须引用原句」没有任何代码在守。**
`schema.py` 对 reason 只有 `min_length=1`。强 prompt 轮统计：仅 18/40 行含探针原文连续 12 字片段。`parse()` 能做字段缺失、枚举越界、数值越界，做不了"是否真的引用了原句"。

## 8. 指标口径（建议固定下来）

| 指标 | 定义 | 用途 |
|---|---|---|
| 结构通过率 | `final_ok=true` / 总条数 | 衡量 parse 层与 prompt 格式约束 |
| 修复触发率 | `repair_count>0` / 总条数 | 衡量偏 prompt / 模型遵守契约的程度 |
| 修复成功率 | 修复后 `final_ok` / 触发数 | 衡量回喂机制本身 |
| 分类一致率 | 与参照版一致 / 总数 | **只是"与参照版一致"，不是准确率** |
| 分类准确率 | 与人工金标一致 / 总数 | 需要先人工标注 20 条才有 |
| 延迟 P50 / P95 | 中位数与 95 分位 | 均值会被外部抖动拉高，不能只看均值 |

上一轮和本轮的"40% / 8/20"都是**一致率**，不是准确率——参照的强 prompt 版本身也不是金标准（它曾把 unknown 从 10 压到 1，属过度归拢）。要得到真正的准确率，必须人工标注一份金标集。

4. **建金标集**：人工标注 20 条探针的正确主题，之后所有对比才有"准确率"可言。
5. **暂缓继续扩词表**：词表已把 unknown 从 10 压到 1，属过度归拢；下一步应加"归类阈值"（必须在摘要中找到可直接引用的证据），而不是继续堆关键词。

## 附录 A：本轮原始落盘字段

```json
{"run_tag":"with_repair","probe_id":0,"repair_count":1,"final_ok":true,
 "error_kind":null,"latency_ms":5946.8,
 "output":{"topic":"hulu","confidence":0.95,"reason":"The note mentions 'Hululu Garden' ..."},
 "error":"1 validation error for TopicResult\ntopic\n  Field required [type=missing, ...]"}
```

注意最后一行：`final_ok=true` 但 `error` 非空。判断成败只看 `final_ok`；`error` 是「最后一次校验错误」，可用来筛出"被回喂救过"的行。
